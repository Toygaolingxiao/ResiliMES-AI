# 《全站页面整理与布局统一规划图》评议稿

评议对象：2026-11-22 版规划图（main 46093b5f 审查）｜评议依据：规划文本本身，未读代码、未跑实机，凡涉及代码事实处均以规划所述为前提｜参照系：IBM Carbon、WCAG 2.2、GOV.UK / Primer / Atlassian 的设计系统治理做法、ISA-101 / ISA-18.2 工业 HMI 与报警管理惯例

## 0. 总评

**一句话判断：诊断扎实，处方偏"整齐"而轻"可信"，施工顺序把最该先做的事排在了后面。**

做得好的地方（应保留）：

- 把症状归并成四个结构性事实，而不是罗列 49 条；"三套视觉语言并存"的定性准确。
- 标杆清单（.sev、#117 字段校验、empty + emptyWhy、"显示 X / 共 Y"）全部取自仓内已落地实现，目标是"做完已经开始的事"，不是外来理想，可信度高。
- 非目标写得克制，WIP=1、每 PR 一种收敛、任一 PR 可回滚，工程纪律好。
- 诚实标注了"未实机渲染""推断"，没有把推演当事实。

需要重点修订的五件事（详见后文）：

1. **证据档位被当成"徽标样式收敛"，实际是数据可信度契约**——应升级为不可绕过的数据不变量，并提前。
2. **P0 功能性静默失败排在波次 4，前面有三波纯视觉收敛**——应拆出热修通道，立即做。
3. **防回潮守卫放在最后一波**——前四波改动期间新代码还在继续漂移（#117 已是先例），应以"棘轮"形式在波次 0/1 就位。
4. **令牌设计按"同义多值→归一"处理，缺语义层**——会把本该分角色的颜色错误合并，并破坏深色主题。
5. **CJK 排版与工业场景几乎未被审视**——行高 1.43、11.5/12px、"回退英文"在日/中文工厂用户面前都是风险点。

## 1. 方法与证据层

**1.1 头条数字口径不干净。** 开篇称"49 条（高 9 / 中 24 / 低 16）"，随后自陈 timeline 问题在两路中重复计数，"归并后"却没有给出去重后的数字。头条应用去重数；附录 A 保留三路原始计数即可。否则读者会拿 49 去估工作量，又拿"高 9"去估风险，两者都被高估。

**1.2 严重度没有评分标尺。** "高/中/低"的判定规则未给出。建议显式采用 **影响面 × 发生频率 × 可逆性** 三因子，并规定：凡会导致用户对系统状态/证据强度做出错误判断的，一律至少为"高"。按此标尺，"cases 页不渲染证据档位"应为高，而"同义绿有 3 个"应为低——现稿的排序恰好相反（档位问题被放在波次 2 的第 ①，但整体叙事仍是视觉一致性）。

**1.3 "三路独立"是分工，不是复现。** 三路按镜头（布局/令牌/交互）切分，互不知晓结论，这能降低相互污染，但并不构成对同一发现的三角验证；重复出现的 timeline 只能说明它显眼。真正的独立性应是：同一镜头由两人各查一遍并比对，或至少对"高"级发现做二次复核。建议对 9 条高发现做一次"挑战性复核"（谁能证伪它）。

**1.4 实机验证必须前移。** 全部结论来自 grep 与计数，.swatch 渲染成矩形、/report 竞态等均为"推演"。波次 1 的验收却依赖"像素级无变化（截图对比）"——而截图基线至今不存在。建议在**波次 0 就建立基线**：Playwright 对「全部页面 × 三语 × 浅/深 × 两档宽度（含 1023）」截图，约几十张，成本很低，却同时解决 (a) 推演类发现的证实、(b) 波次 1–3 的回归对比、(c) 波次 5 复审的起点。现稿把实机放在最后，等于前四波是蒙眼施工。

**1.4.1 度量的是"代码卫生"，不是"用户结果"。** 80 种 hex、112 处硬编码、间距占比，都是实现侧指标。现稿没有任何一条"用户任务"视角的验收：值班长在失败后能否在 10 秒内知道发生了什么、能否重试？计划员能否分辨某个结论是记录还是推断？这些才是该系统真正的成败。见第 9 节。

## 2. 优先级与波次结构

**2.1 P0 不能排队。** "run() 失败后 paint() 擦掉状态行"是确定性代码路径、全站最核心动作的静默失败，规划自己也标了 P0，却放在波次 4（排在令牌、组件、骨架之后），且受 WIP=1 约束。这是**优先级倒挂**：美观收敛可以等，用户重排失败而不知情不能等。建议：

- 设立**热修通道**，不受 WIP=1 约束：PR-4a（静默失败 + 重试入口）、/report 在途防护（seq token）、"无效 lot 进最近查看"这类行为缺陷，作为"波次 H"在波次 0 之前或并行完成。
- WIP=1 约束的是**视觉收敛**类 PR（它们互相冲突面大）；功能缺陷修复与其文件冲突小，可并行。

**2.2 4b 与章程工作线 1 的依赖写得过于松。** "若工作线 1 先行则并入"是条件句，会在实际排期中变成互相等待。应在波次 0 就定：谁先、谁并入，落到具体 PR 编号与负责人。

**2.3 守卫应走"棘轮"，而不是"终点验收"。** 波次 5 才引入 CSS 守卫（定义外 hex、表外字号/间距、基线外断点），意味着波次 1–4 的十几个 PR 期间，团队其他人仍在往仓里加新的偏差；规划自己也承认 #117 的新代码就这样漂移了。做法：

- 波次 0 用 stylelint（或简单脚本）**记录当前违规数作为预算**写进 CI，只允许单调下降，新增即红；
- 每个收敛 PR 顺手把预算往下调；
- 波次 5 只是把预算降到 0 并去掉豁免。

这样"防回潮"从终点变成全程机制，收益远大于成本。

**2.2.1 总量与吞吐。** 约 25 个串行 PR、每个都要截图对比与双主题核对。若无自动化截图，人工核对会成为瓶颈，WIP=1 会把总工期拉得很长。这再次说明 1.4 的基线必须先行，并考虑让"纯令牌化、零视觉变化"的 1a/1b/1c 并行（它们改的文件不同，且有像素对比兜底）。

## 3. 令牌与设计系统架构

**3.1 缺语义层——"同义同值"的处方可能是错的。** 现稿把"完成绿有 3 个（--good #198038、.pill 的 #a7f0ba 对、#24a148）"视为需要归一的冗余。但这三者很可能是**不同角色**：深绿作文字（白底高对比）、浅绿作填充底色、中绿作图形/图标。把它们合并成"一个值"会直接损失对比度或层次。正确的做法是分三层：

| 层 | 例 | 作用 |
| --- | --- | --- |
| 原始（primitive） | green-30 / green-50 / green-60 … | 色板，不直接被组件引用 |
| 语义（semantic） | --support-success、--text-success、--bg-success-subtle、--border-success | 按**角色**命名，主题切换只改这一层映射 |
| 组件（component） | --pill-done-bg、--tier-record-fg | 可选，仅当组件需要偏离语义层时 |

"同义同值"应改为"**同角色同令牌**"。这也让 #684e00 的决策自然落位：它是一个**文字角色**（--text-warning），而不是"要不要新增一个颜色"。

**3.2 深色主题不能靠"逐项核对"。** 波次 1b 的深色验收是人工核对。语义层建好后，深色应是**一张映射表**（语义 → 深色原始值），并配自动对比度检查：每个文字语义令牌 × 其常用背景令牌，在两个主题下计算 WCAG 对比度（文字 ≥ 4.5:1，大字 ≥ 3:1，非文字 ≥ 3:1），低于阈值 CI 失败。#684e00 的"高于 4.52:1"现在是推断，应改为脚本计算的结论。

**3.3 单一令牌源应该是数据文件，不是文档。** 规划要求"文档与代码不一致视为缺陷"，但文档与代码天然会漂移。更稳妥的架构是：**tokens.json（W3C Design Tokens 格式）为唯一源**，用 Style Dictionary 之类的生成器产出 CSS 变量、JS 常量、甚至 docs 里的令牌表。这样：

- 波次 1c"JS 色板单源化"不再是一次手工迁移，而是生成物；
- "二选一写死：构建时常量或 CSS 变量读取"这个悬而未决的点有了答案（见 3.4）；
- DESIGN\_SYSTEM.md 的令牌部分变成生成物，"文档与代码一致"由构建保证。

**3.4 canvas 取色的坑。** timeline 的 canvas 不能使用 var()；"构建时常量"会固化浅色值，主题一切换就错；"CSS 变量读取"必须在每次主题切换时重读并重绘，且要缓存（getComputedStyle 在热路径上昂贵）。建议写死为：**运行期读取 + 缓存 + 监听主题变更事件重绘**；数据色板（甘特条、热力格）走独立的 chart palette 令牌，并为浅/深各定义一套。

**3.5 间距：别把"var() 引用"当目标。** 附录里 4/8/12/16 的数值占比其实不低（styles 60%、report 71%），说明团队**数值上已基本遵守**，问题主要是"没有用 var() 引用"。强制为每个 padding 都写 var(--s2) 的收益有限，可读性反而下降。更高性价比的做法：用 lint 限定**允许的数值集合**，而不是强制引用形式；令牌只留给跨组件复用的值。

**3.6 对间距决策的实质意见。** 决策点 2 是个假二选一。Carbon 的间距阶梯是 2/4/8/12/16/24/32/40/48，**没有 6 与 10**；6px/10px 之所以高频，往往是因为组件高度/行高没有被先定下来，内边距在"凑"高度。更根本的做法是先定**控件与行的高度阶梯**（如 24/32/40/48，.run 的 min-height 32px 已是其一），再由高度反推内边距。这样 6/10 多半自然消失，不必追认成基线。若确需密度模式，应做**紧凑/默认两档整体切换**，而不是在基线里塞更多零散数值。

**3.7 规划第三节与决策点 2 自相矛盾。** 第三节已写死"只允许 0 与 4/8/12/16"，同时其例外清单含 12px 14px、6px 8px、24px 32px——14、24、32、6 都在 4 档之外，等于事先把决策点 2 的答案写进了"终态"。要么先定决策再写终态，要么在终态里标注"待决策 2"。

## 4. 证据档位：从样式收敛升级为数据契约

这是全稿最该提高权重的一条。"記録 / 観測帰因 / 不明"不是装饰徽标，而是**认识论状态**：它告诉用户眼前这个结论是被记录下来的事实、是由观测推断出来的归因，还是根本不知道。规划发现 cases 页完全不渲染档位、控制台 AI 面板降级为无色的通用 chip——这意味着用户可能把**推断当记录**读。在做 AI 诊断/归因的工业系统里，这是**可信度与责任**问题，不是一致性问题。

建议：

1. **契约化**：所有"结论/陈述类"载荷必须带 tier 字段；前端渲染函数在 tier 缺失时\*\*失败安全地显示"不明"\*\*而不是不显示。契约测试覆盖"无 tier → 渲染为不明"。
2. **单一渲染入口**：只有一个 renderTier()，所有页面调用；grep 不到其他实现。
3. **位置规则**：档位紧贴结论本身（行内、数字旁），不放在远端的"证据"列，不放在悬停里。
4. **非颜色冗余**：三档用形状/文字/图标区分，打印黑白与色盲下仍可辨（WCAG 1.4.1）；.sev 的"3px 左边非颜色维度"是现成范例。
5. **时间提前**：从波次 2 的第 ① 个组件提前到"热修通道"或至少波次 1 之后立即做，且不依赖按钮/表格的收敛。
6. **降档需可解释**：当结论由记录降级为推断时，UI 应能说明为何（缺哪类记录），这与"错误四要素"同构。

## 5. 状态纪律八条：评价与补强

八条总体正确，是本稿最有价值的部分。需补强的缺口：

- **陈旧数据**：只在"错误"里提到旧数据标"未更新"。应独立成一条：任何展示的数据都有**时间戳与新鲜度状态**（实时 / 缓存 / 已过期），对排程这类时变系统尤其关键。
- **长耗时动作的完整生命周期**：加载三件套写了文案+量级+取消，但排程仿真（历史上 20 分钟、现 5 分钟内）这类动作还需要**可取消、可恢复（刷新页面不丢）、完成后的通知**。建议明确：作业 ID、后台运行、返回后能找回结果。
- **破坏性/高影响动作**：重排是有后果的变更。规范中没有"预览差异→确认→可撤销"的模式。建议补一条：改变排程的动作先给 diff（变了哪些订单/设备/交期），再提交；提交后给出回滚入口。
- **status 与 alert 的使用边界**："各一"可行，但需规定何时用 alert（打断型，仅限用户必须立刻知道的错误），避免 alert 泛滥导致读屏用户被反复打断；GOV.UK 的"错误摘要置顶并移焦"模式可借鉴到多字段表单。
- **重绘保状态**列为标杆很好，但应从"控制台两处"扩成全站规则，并进入契约测试。
- **截断**："显示 X / 共 Y"之外，需规定**数值截断时的排序依据**（按什么取前 N），否则用户无法判断被藏起来的是不是更重要的。

## 6. 多语言与 CJK 排版

这是现稿最薄的一块，而用户群显然是中日英三语的制造现场。

**6.1 行高 1.43 对 CJK 偏紧。** 1.43（20/14）是拉丁文字的 Carbon 取值。日文/中文正文通常需要 1.6–1.8，数据表格内可收到 1.5 左右。把行高"收敛为 1.43/1.5 两值"会让日文长句拥挤。建议按语言分配行高令牌（lang 属性切换 --lh-body），而不是全站一值。

**6.2 小字号。** 11.5/12px 对汉字与假名的可读性很差（笔画密度高），规划把 11.5→12、12.5→13 只是"入阶"。建议规定 **CJK 最小字号 12px，正文 13–14px**；fab 视图若用于大屏/远距离观看，则要按观看距离重新定字阶，而不是在桌面字阶里取最近的档。请在波次 0 先回答：fab 视图的使用场景是工位还是看板？

**6.3 IBM Plex 不覆盖 CJK。** "接入 IBM Plex"只解决拉丁字符与数字；汉字/假名会落到系统字体，且各平台不同。需要显式定义 CJK 字体栈（如 IBM Plex Sans JP / Noto Sans CJK / 系统黑体），以及混排的基线对齐；数字列必须 font-variant-numeric: tabular-nums，否则表格列无法对齐（这也关系到"数字列右对齐全站有效"）。

**6.4 回退政策。** 统一为"缺键回退英文"在逻辑上简单，但对日本/中国现场用户，缺键时跳出英文比跳出相邻语言更糟。更稳妥的是：**缺键在 CI 里直接失败（目录已 1025 键零缺失，说明做得到）**，运行期回退仅作兜底并上报；对服务器字符串走"原文 + 来源标注 + 本地化白名单"，规划已提及，保留即可。

**6.5 用平台能力，不手写格式器。** 时长/数字/日期的"三合一格式器"建议直接建立在 Intl.NumberFormat（unit 样式）、Intl.DateTimeFormat、Intl.RelativeTimeFormat 上，而不是再手写第四套。需注意日文的数字单位习惯与中文万/亿的差异。

**6.6 版式韧性。** 三语文案长度差异大（英文常最长、中文最短），按钮/表头/徽标要有最长文案的版式测试；日文需要 line-break: strict 与 word-break 策略，避免禁则处理失控。建议在截图基线里加入"伪本地化（拉长 30–40%）"一档，专门暴露溢出。

## 7. 无障碍

现稿的"无障碍底线"三条方向对，但低于 WCAG 2.2 AA 的实际要求。建议明确对标并逐条落地：

- **1.4.3 / 1.4.11**：文字对比 4.5:1，**徽标边框、图表元素、焦点环等非文字 3:1**（档位与状态点尤其容易漏）。
- **2.4.7 / 2.4.11**：焦点可见，且**不被粘性顶栏或浮层遮挡**（2.2 新增）；规划要求 48px 顶栏与 panel 滚动统一，正好踩在这一条上。
- **2.5.8**：目标尺寸不小于 24×24 CSS px，注意 4px 8px 内边距的紧凑控件与表格行内按钮。
- **1.4.13**：悬停/聚焦出现的内容须可关闭、可悬停停留、不消失；规划把 timeline tip 列为悬停模型，需同时满足键盘触发。
- **3.3.1 / 3.3.3 / 4.1.3**：错误识别、错误建议、状态消息——#117 已基本达标，推广时直接引用。
- **canvas 无语义**：甘特图是 canvas，读屏与键盘用户完全无法访问。至少提供**等价的表格视图**（按设备/时间列出任务），并说明这是替代而非补充。
- 其余：forced-colors（高对比度模式）下的徽标不应丢失；prefers-reduced-motion 已列入，保留。

## 8. 领域缺口：这是排程/工业控制台，不是一般后台

规划几乎全部用"通用设计系统"的语言描述问题，缺少与领域对话的部分。可借鉴工业 HMI 的成熟惯例：

- **颜色是稀缺资源（ISA-101）**：高性能 HMI 的原则是正常状态用低饱和中性色，**颜色只留给异常**。规划里完成绿/运行蓝/琥珀/警戒红并列，容易让"正常"也满屏彩色，削弱真正异常的显著性。建议在令牌层把"状态色"和"装饰/分类色"分开，并规定正常态默认中性。
- **报警管理（ISA-18.2 / EEMUA 191）**：严重度分级、报警泛滥、确认（ack）、抑制与重新触发，是现场用户的既有心智。.sev 作为标杆值得肯定，但应补一份**严重度语义定义**（每级对应什么响应时限与动作），否则颜色只是颜色。
- **按角色的信息层级**：值班长（实时、少而急）、计划员（对比、可追溯）、管理者（汇总）。现稿用"全站统一"覆盖了所有角色；骨架统一没问题，但每个角色的**首屏信息层级**应单独定义（"一眼要看到什么"）。
- **排程特有的呈现**：版本对比/差异、冲突与约束违反的解释、what-if 与已提交方案的区分、重排影响范围。这些恰恰是"AI 排程"用户最关心、也最需要证据档位的地方，应列为设计系统要覆盖的**领域组件**（如 diff 行、约束违反卡、方案状态条），而不只是通用 .card/.kpi。
- **"可停止"的控制感**：对 AI 驱动的排程，用户需要明确的"停止/接管/回滚"位置与状态。这属于 4.0 中"破坏性动作"与"长耗时动作"的延伸，建议作为一等公民纳入骨架（顶栏或状态行固定位置的停止入口）。

## 9. 验收与度量

波次 5 的"零高发现"以同一套审查口径评判，是**自证式**验收。建议增加：

1. **三个关键任务的认知走查（每个由未参与开发的人执行）**：①重排失败后恢复；②读懂一条结论的证据档位并说出依据；③对比两个排程版本找出变化。记录完成时间与卡点。
2. **5 秒测试**：各页首屏，问"这页在说什么、有什么异常"。
3. **度量**：违规预算降为 0；档位渲染覆盖率 100%（契约测试）；截图回归零非预期差异；对比度脚本零失败；任务走查通过。
4. **窄幅**：规划把约 400px 排除在外是合理的，但需在文档中写明"不承诺"而非"未验证"，避免被误读为已支持。

## 12. 建议的修订版波次（精简）

**波次 H（立即，不受 WIP=1 约束）**：PR-4a 主流程静默失败 + 重试入口；/report 在途防护；无效 lot 不进最近查看；cases 证据档位失败安全渲染（先保证"不明"可见）。

**波次 0（文档 + 基础设施）**：截图基线（页面 × 三语 × 两主题 × 宽度 × 伪本地化）；违规预算棘轮入 CI；决策点 1–5 定版（按第 10 节意见）；确定 tokens.json 单一源与生成链路；严重度评分标尺与去重后的发现计数。

**波次 1（令牌层）**：先建语义层与深色映射表 + 对比度脚本，再做 1a/1b/1c（可并行）；canvas 取色改运行期读取。

**波次 2（组件）**：档位 .tier 与 renderTier 契约（升级为数据契约）→ 按钮/输入 → 表格（含 tabular-nums）→ 徽标族 → 卡片/浮层。每 PR 同步更新组件画廊页。

**波次 3（骨架）**：timeline → report/import → 控制台内部 → fab；增加窄幅与焦点不被遮挡检查；甘特图补等价表格视图。

**波次 4（状态与文案）**：补充陈旧数据、长耗时作业生命周期、变更预览/回滚三条规范；i18n 单一回退 + CI 缺键失败 + Intl 格式器；CJK 版式令牌（行高、字体栈、最小字号）。

**波次 5（收口）**：预算归零；三项关键任务走查 + 5 秒测试；实机三语两主题复审；文档与代码一致性由生成物保证。

另建议配一页**组件画廊**（kitchen-sink，路由如 /design），按组件 × 状态（默认/悬停/焦点/禁用/加载/错误）× 主题 × 语言展开。它同时是截图回归的对象、评审的单一入口和新人的参照物，是 Primer、Atlassian 等成熟体系防止漂移的核心设施，且对本仓的三套体系并存问题尤其有效。

## 13. 结语

这份规划的底子很好：它正确识别了"目标已在仓内，缺的是做完"。要把它从"一致性整理"提升到"可信的工业控制台"，关键是三件事——**把证据档位当契约、把 P0 行为缺陷移出视觉收敛的队列、把防回潮与实机基线从终点前移到起点**。其余意见（语义令牌层、CJK 版式、WCAG 2.2、工业 HMI 惯例）是在此之上把系统做得更经得起现场检验的补强。
